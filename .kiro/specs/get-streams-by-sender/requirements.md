# Requirements Document

## Introduction

This feature adds a sender-indexed lookup to the `StellarStreamContract` Soroban smart contract. Currently, the contract stores streams by numeric ID only — there is no way to query which streams belong to a given sender without scanning the entire ledger. The feature introduces a `SenderStreams(Address)` variant in the `DataKey` enum that persistently stores a `Vec<u64>` of stream IDs for each sender. Both `create_stream` and `create_split_stream` are updated to append new stream IDs to this index at creation time. A new public method `get_streams_by_sender` exposes this index to callers. Finally, `docs/CONTRACT_BINDINGS.md` is updated to document the new method and its TypeScript binding.

## Glossary

- **StellarStreamContract**: The Soroban smart contract defined in `contracts/src/lib.rs` that manages payment streams on the Stellar network.
- **DataKey**: The `#[contracttype]` enum that determines persistent storage keys for the contract.
- **SenderStreams**: The new `DataKey` variant — `SenderStreams(Address)` — that maps a sender's `Address` to a `Vec<u64>` of stream IDs they have created.
- **Stream**: The `#[contracttype]` struct representing a single payment stream with sender, recipient, token, amounts, and timing.
- **Sender**: The `Address` that funds and initiates a stream via `create_stream` or `create_split_stream`.
- **Stream ID**: A `u64` integer assigned sequentially by the contract; uniquely identifies a stream.
- **Persistent Storage**: Soroban's `env.storage().persistent()` tier, which survives ledger archival, in contrast to instance or temporary storage.
- **Split Stream**: A stream created via `create_split_stream` that distributes a total amount across multiple recipient child streams, all attributed to a single sender.
- **Child Stream ID**: Each individual stream ID produced inside `create_split_stream` for a recipient allocation.

## Requirements

### Requirement 1: SenderStreams Storage Key

**User Story:** As a smart contract developer, I want a dedicated persistent storage key per sender, so that stream IDs can be accumulated and retrieved efficiently without changing the `Stream` struct.

#### Acceptance Criteria

1. THE `DataKey` enum SHALL contain a `SenderStreams(Address)` variant.
2. THE `StellarStreamContract` SHALL store the `SenderStreams` index in persistent storage (not instance or temporary storage).
3. WHEN a `SenderStreams` entry does not yet exist for a given sender, THE `StellarStreamContract` SHALL treat the missing entry as an empty `Vec<u64>`.

---

### Requirement 2: Index Update on `create_stream`

**User Story:** As a stream sender, I want every stream I create to be automatically registered under my address, so that I can later retrieve all my stream IDs in one call.

#### Acceptance Criteria

1. WHEN `create_stream` is called with a valid sender, THE `StellarStreamContract` SHALL append the newly assigned stream ID to the sender's `SenderStreams` list in persistent storage.
2. WHEN `create_stream` appends to the sender's `SenderStreams` list, THE `StellarStreamContract` SHALL perform the update after writing `DataKey::Stream(next_id)` and before publishing the `StreamCreated` event.
3. WHEN `create_stream` is called multiple times by the same sender, THE `StellarStreamContract` SHALL accumulate all stream IDs in the same `SenderStreams` entry in the order they were created.
4. WHEN `create_stream` is called by different senders, THE `StellarStreamContract` SHALL maintain separate `SenderStreams` entries for each sender without cross-contamination.

---

### Requirement 3: Index Update on `create_split_stream`

**User Story:** As a stream sender using split streams, I want all child stream IDs generated by `create_split_stream` to appear in my sender index, so that my full stream history is accessible through a single lookup.

#### Acceptance Criteria

1. WHEN `create_split_stream` is called with a valid sender and N recipients, THE `StellarStreamContract` SHALL append all N child stream IDs to the sender's `SenderStreams` list in persistent storage.
2. WHEN `create_split_stream` appends child IDs, THE `StellarStreamContract` SHALL add them in the same order that child streams are created (i.e., matching the order of the `recipients` input vector).
3. WHEN a sender calls both `create_stream` and `create_split_stream`, THE `StellarStreamContract` SHALL include stream IDs from both calls in the same `SenderStreams` list.

---

### Requirement 4: `get_streams_by_sender` Query Method

**User Story:** As a developer or frontend client, I want to call `get_streams_by_sender(sender)` to retrieve all stream IDs created by that address, so that I can display or process a sender's streams without off-chain indexing.

#### Acceptance Criteria

1. THE `StellarStreamContract` SHALL expose a public method `get_streams_by_sender(env: Env, sender: Address) -> Vec<u64>`.
2. WHEN `get_streams_by_sender` is called for an address that has created at least one stream, THE `StellarStreamContract` SHALL return a `Vec<u64>` containing exactly the stream IDs created by that sender, in creation order.
3. WHEN `get_streams_by_sender` is called for an address that has never created a stream, THE `StellarStreamContract` SHALL return an empty `Vec<u64>` without panicking.
4. WHEN `get_streams_by_sender` is called, THE `StellarStreamContract` SHALL read from persistent storage using the `SenderStreams(Address)` key.

---

### Requirement 5: Scalability via Persistent Storage

**User Story:** As a power user, I want the sender index to scale to 100 or more streams per sender without performance degradation or storage failure, so that the feature remains usable for high-volume senders.

#### Acceptance Criteria

1. THE `StellarStreamContract` SHALL store `SenderStreams` data in persistent storage so that ledger archival does not silently drop the index.
2. WHEN a sender has created 100 or more streams, THE `StellarStreamContract` SHALL store all 100+ stream IDs in the single `SenderStreams(Address)` persistent entry rather than using multiple keys.

---

### Requirement 6: Documentation Update

**User Story:** As a frontend developer, I want `docs/CONTRACT_BINDINGS.md` to document the `get_streams_by_sender` method, so that I know the TypeScript signature and can integrate it into the frontend without reading Rust source code.

#### Acceptance Criteria

1. THE `docs/CONTRACT_BINDINGS.md` file SHALL include a row for `get_streams_by_sender` in the "Generated methods" table with its TypeScript signature and a "Read-only" note.
2. THE `docs/CONTRACT_BINDINGS.md` file SHALL include a TypeScript usage example demonstrating how to call `get_streams_by_sender` and iterate over the returned stream IDs.
